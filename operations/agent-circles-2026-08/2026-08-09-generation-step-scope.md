## 1. The fixed design — settled, cited, not re-opened

> **RULED 2026-08-09 — confirmed in full.** *"All twelve items carry forward unchanged. The Q1 hard constraint is confirmed at the exact point of temptation. The QW-A verbatim carry is confirmed complete. The validation/standing-runner boundary is confirmed honoured throughout. Nothing in §1 is re-opened."*

Nothing in this section is proposed for re-opening. Each item cites its ruling.

1. **Architecture: externally-driven; generation runs in the runner.** The loop lives outside SageReasoning's servers; the calling process holds cycle state and the continue/stop decision; SageReasoning stays stateless and request-scoped, providing only *"the examination, the novelty check, and the trust-event write"* per cycle (the 2026-08-05 ruling; brief §1.1). A direct consequence, settled with it: **the generation step runs in the runner** — SageReasoning makes no generation call, hosts no heuristic, and never sees the runner's model. The generation model is runner-owned configuration, outside AC1's server-side model-selection table by construction.
2. **Seven heuristics, one candidate each per cycle; the six core all run each cycle** (heuristics doc + brief §1.3): analogous transfer, combinatorial generation, synthesis over novelty, context transfer, fifth-circle weighting, anomaly detection, friction detection. A richer pool, not one-per-cycle selection.
3. **Friction detection is structurally different** (heuristics doc, ruled): preferred-indifferent tag at generation time, not a virtue-domain tag; a candidate that never engages a virtue domain remains a valid task candidate — kathekon vs. katorthoma, applied to generation. The type encodes this as a discriminated union (`initialClassification`), so a friction candidate structurally cannot be forced into the virtue-domain shape.
4. **The examination-cost shape, ruled 2026-08-05:** all candidates pass **the guardrail shape only** (proximity + virtue-domain assessment, no Layer-3 prose); novelty runs on all guardrail-shaped survivors; **the highest-proximity candidate that also passes the novelty threshold** receives the one full examination, whose Layer-3 prose is the cycle's human-legible dashboard result. **G4 is a HARD CONSTRAINT** (ruled with the brief): the full examination is an independent examination, not a confirmation step — what it finds stands.
5. **The null-cycle rule, ruled:** if no candidate passes the novelty threshold, the cycle records a **null cycle** and never falls back to presenting the best non-novel candidate as a result. §2.6 below discharges the carried obligation that this rule be **architecturally enforced, not merely stated as policy** (the brief §1 confirmation's carry-forward note (i)).
6. **The fallback rule, with QW-A's settled semantics folded in verbatim** (heuristics doc + the `watching` ruling, carried per its own instruction): three consecutive null cycles from heuristics 1–6 → friction-detection-only mode, until a non-null cycle returns from an active mechanism. QW-A (settled ground — carry, do not re-open): **(i)** a `dependency_unavailable` cycle passes the counter **transparently — the chain neither advances nor resets**: *"The counter's purpose is detecting novelty exhaustion of heuristics 1–6. A dependency outage carries no information about novelty. Counting it toward the trigger would mean an infrastructure failure could push the loop toward friction-only mode — the exact mechanism whose dependency failed. Option (b) is equally wrong in the other direction: a sustained outage could silently erase evidence of genuine novelty exhaustion by repeatedly resetting the chain. Option (c) is the only reading that keeps the counter honest about what it is measuring."* **(ii)** the cycle-level outcome reads `dependency_unavailable` *"only when no active heuristic could produce an assessable pool"* — concretely, friction-only mode with the task list down; in normal mode a task-list outage is candidate-level only and the cycle outcome comes from the other six heuristics. A friction-only-mode `dependency_unavailable` cycle neither satisfies nor disturbs the fallback-exit condition: *"It is not a non-null result from an active mechanism. It is not a null cycle. It is a third thing — an honest record of infrastructure unavailability — and the counter treats it as transparent."*

## 2. Proposals for the mentor (PROPOSAL throughout — nothing decided here)

### 2.1 Per-heuristic implementation shape — fixed templates, named inputs, a uniform output contract

**PROPOSAL:** each heuristic is realised as a **fixed prompt template** the runner's own model executes — one template per heuristic, three parts each:

1. **A fixed instruction stanza** — the heuristic's own question, verbatim-faithful to the heuristics document (e.g. analogous transfer: *"given the `OikeiosisGap`, what existing capability could be applied to address it in a way it has not been applied before?"*). The stanza is fixed text; it never varies cycle-to-cycle (§2.4's variation touches input presentation only, never instructions).
2. **Named input slots** — what the template consumes, per the table below. The inputs come from exactly three ruled sources: the gap (all three fields — `currentCircle`, `targetCircle`, `targetCircleMeaning`), the runner's **knowledge context** (defined below), and — for heuristic 7 only — the handed-in task list.
3. **A uniform output contract** — exactly one candidate per template execution: `proposedAction` (plain language, a not-yet-taken action), `initialClassification` (the discriminated union — `virtue_domain` with the engaged domains for heuristics 1–6; `preferred_indifferent` for heuristic 7), and `generationConfidence` (0.00–1.00, with the approved type's own caveat carried into the template text so the runner's model does not inflate it: *a generation-time relevance signal only — NOT a probability, NOT a prediction of the examination outcome*). The template output populates a `GeneratedCandidate` with `cycleOutcome: 'pending'` and the settled `gapRef` format; `targetCircle` inherits the gap's value by construction (the approved type's rule — never re-derived per candidate).

**The knowledge context, defined** (a named term this document introduces so the input slots are concrete): the runner-held corpus the heuristics draw on — the project materials the runner operates on (repo, documents, whatever the founder's runner environment holds), the runner's **own** prior-cycle records (its `GeneratedCandidate` history and per-cycle outcomes, which the runner holds as cycle state per the architecture ruling), the runner's **own** accrued generative-prompt seeds (own-identity only, or founder-exported — Q8's ownership boundary, restated not re-litigated), and the handed-in task list. It is runner-owned and external by construction; no server read exists for it beyond the ruled per-cycle seams.

### 2.2 Candidate pool size — and the friction-multiplicity question

**PROPOSAL:** the normal-mode pool is **up to seven candidates** — six core heuristics plus one friction candidate when the task list is available. This is now proposed as the fixed per-pass count (the `fresh` scope's [PR19] note struck "up to seven" as an unverified inference *because the generation step was unscoped*; this document is where the count becomes a scoped proposal rather than an inference). A task-list outage in normal mode drops the friction candidate to candidate-level `dependency_unavailable` (`unavailableDependency: 'shared_task_list'`) and the cycle proceeds on six (QW-A(ii), settled).

**In friction-only mode the pool composition is genuinely under-determined by the corpus, and the tension is disclosed rather than silently resolved:** the ruled mechanism says *one candidate per heuristic* per cycle, but the heuristics document's own friction definition says *"Each friction point generates one candidate."* In normal mode the one-per-heuristic rule governs (proposed; the friction template selects one qualifying friction point per §2.3–2.4). In friction-only mode, a single-candidate pool would make the filtering pass degenerate (novelty and proximity comparison over a pool of one) — the AI proposes friction-only mode generates **one candidate per qualifying friction point, capped at seven per cycle** (the cap keeps the filtering-pass cost profile inside the ruled normal-mode shape: the brief's stated per-cycle cost floor — *"a cycle costs at minimum six guardrail calls + up to one full consult"* — is not exceeded in the mode designed to be the cheap backstop). **§3 QG-B puts this to the mentor** — it touches the ruled one-per-heuristic mechanism, so it is not defaulted here.

**RULED 2026-08-09 — §2.2 confirmed; QG-B ruled here: one candidate per qualifying friction point, capped at seven per cycle, in friction-only mode.** *"Normal-mode pool of up to seven candidates confirmed as the fixed per-pass count. Task-list outage in normal mode → friction candidate to `dependency_unavailable` at candidate level, cycle proceeds on six — confirmed per QW-A(ii)."* On the textual tension: *"The textual tension resolves in favour of one-per-friction-point in friction-only mode — the one-per-heuristic rule was written for a context where friction is one of seven heuristics, not the sole active mechanism. This is not an amendment to the ruled mechanism; it is the correct application of the mechanism's purpose to a mode the original text did not explicitly address."*

### 2.3 The friction-detection threshold

**PROPOSAL:** qualitative and binary in v1 — no numeric threshold. The heuristics document defines a friction point by three markers (*a step that takes longer than expected, produces an unsatisfying result, or requires workaround behaviour*), and the `SharedTask` contract carries friction as plain language (`frictionAssessment.description`), so there is no measured quantity a numeric threshold could bind against. Proposed operational test — **a friction point qualifies for candidate generation when the runner can name all three of:**

1. the **task** it belongs to (a `SharedTask` with `frictionAssessment.detected: true`),
2. the **specific step** exhibiting the friction, and
3. **which of the three markers** it exhibits (slow / unsatisfying / workaround).

A friction observation that cannot fill all three slots is not yet a friction point — it stays on the task's `frictionAssessment` as material for a later cycle rather than generating a vague candidate (the same discipline as the sage-compass `concrete`/`vague` gate, applied at generation: a candidate must propose removing a *named* friction, not "improve the workflow").

**Selection among multiple qualifying points (normal mode, one candidate):** under the cycle's phantasia draw (§2.4), not a fixed recency rule — deliberate variation in which friction point is examined, rather than the same top-of-list point winning generation every cycle. **Dedup guard:** a friction point already converted into a candidate in a prior cycle is not re-converted unless its `frictionAssessment` has been refreshed since (`assessedAt` newer than the prior candidate's cycle) — without this, the loop's friction channel would resubmit one stubborn friction point indefinitely and the novelty check would burn a server call per cycle re-rejecting it.

**Numeric thresholds are deferred to validation-run data** — if the bounded run shows the qualitative test either floods (too many qualifying points) or starves (none qualify), that evidence, not anticipation, sizes any numeric bound (the same waits-for-data posture the `fresh` window ruling took).

**RULED 2026-08-09 — §2.3 confirmed as proposed.** *"Qualitative and binary in v1 confirmed. Three-slot operational test confirmed — task, specific step, which marker. Dedup guard on `assessedAt` confirmed as a required structural element, not optional discipline. Numeric-threshold deferral to validation-run data confirmed."*

### 2.4 The `randomOffsetPercent` phantasia-variation mechanism

The parameter's two ruled purposes (config scope A.2): anti-synchronisation jitter, and *"introducing phantasia variation into the generation step's input sequence"* — the second explicitly deferred to this document (config scope A.3). **PROPOSAL — one random draw per cycle, used twice:**

1. **Timing (the standard purpose):** the runner draws `r ∈ [0, randomOffsetPercent]` once per cycle and stretches the interval: `actualInterval = minimumInterval × (1 + r/100)`. **Additive-only jitter, deliberately:** `minimumInterval` is a *minimum* — symmetric jitter would let the offset violate the parameter's own name and its throttling purpose. (Anti-synchronisation needs only decorrelation, which one-sided jitter provides.)
2. **Input sequence (the phantasia purpose):** the same draw seeds a deterministic per-cycle permutation applied to **presentation order and selection, and nothing else**: the order in which knowledge-context elements are presented in the input slots of heuristics 1–6; heuristic 2's cross-domain **pair selection**; heuristic 4's capability selection; heuristic 7's selection among qualifying friction points (§2.3). The stated rationale made concrete: what an LLM-driven generation step attends to varies with what it is shown first and what it is shown together — varying presentation of the same material across cycles is exactly "phantasia variation into the input sequence," without varying anything load-bearing.

**Never varied, by construction:** the gap (direction is human-authored, never perturbed); the instruction stanzas; the output contract; any threshold; anything examination-side (the server seams neither see nor consume the draw — variation is confined to the runner's own composition of generation inputs). This confinement is a required review dimension at build (§2.11).

**Why one draw rather than two:** a single per-cycle seed makes the cycle's variation *reproducible from its record* — the runner can log the seed on its own cycle state (and may include it in the `watching` row's build-time details), so an anomalous cycle's input composition can be reconstructed during the validation run rather than being unrecoverable randomness.

**RULED 2026-08-09 — §2.4 confirmed as proposed.** *"One random draw per cycle used twice confirmed. Additive-only jitter confirmed. Deterministic per-cycle permutation applied to presentation order and selection only confirmed. Confinement list confirmed and carried into §2.11 as a required review dimension. Single-seed reproducibility confirmed as a build requirement."*

### 2.6 The null-cycle rule's architectural enforcement (carried obligation — the brief §1 confirmation's note (i))

The rule must be **enforced, not stated**. **PROPOSAL — three structural layers, none of them policy:**
