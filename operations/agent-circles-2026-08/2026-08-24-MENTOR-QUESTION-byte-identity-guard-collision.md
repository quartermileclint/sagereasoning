## The question

**The guard has no defined end.** It was raised to protect an observation window whose capture is
**stopped**: `GATE1_FALSE_HOLD_CAPTURE` is unset in the founder-loop configuration (verified — the
key is absent from both `settings.local.json` and the canonical hooks backup), and the 130-record
buffer was **frozen as evidence** at `runs/2026-07-17/`. The record states that any part-(3)
re-measurement needs a **new** window (register item P6), not a resumption of the old one.

**So:** if the window the guard protects is closed, does the guard still bind — and if it does, what
condition ends it? Three shapes, none chosen here:

1. **The window is over; the guard is retired or narrowed.** Both blocked items then apply normally,
   each on its own tier (the citation fix is `governance`-adjacent to a data corpus; the L4 header is a
   comment-only edit inside `trust-core`).
2. **The guard stands until P6 opens a new window**, on the reasoning that a future window's baseline
   should be comparable to the frozen buffer's. Both items stay blocked, and **the blockage is
   indefinite**, since P6 is not scheduled.
3. **The guard admits a bounded exception class** — e.g. a correction that fixes a *factual defect*
   (a wrong citation) or that changes *no executable line* (a comment) is admissible, while any
   behavioural change is not. This would need the exception defined tightly enough that it cannot be
   invoked for convenience.

**Why this is put rather than resolved.** A ruling elevated the citation defect *within* its gate
constraint, *"exactly as ruled"* — which reads as a deliberate refusal to route around the guard, not
an oversight. Deciding the guard has expired would reverse that refusal on AI judgement. **The
collision was surfaced for the founder rather than routed around, and it stayed surfaced. It now
needs a ruling to move.**
