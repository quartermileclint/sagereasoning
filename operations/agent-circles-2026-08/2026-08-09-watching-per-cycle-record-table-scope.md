## 2. Proposals for the mentor (PROPOSAL throughout — nothing decided here)

### 2.1 Schema shape — a cycle table plus a candidate table

**PROPOSAL: two tables**, `idea_loop_cycles` (one row per cycle) + `idea_loop_candidates` (one row per generated candidate, FK → its cycle row). The prompt's named tension — a cycle-level row vs Q7's per-candidate rejected-guardrail-result requirement — resolves cleanly this way: the cycle row carries the four ruled cycle-level facts (outcome, cost, elapsed-vs-max, `loopId`), and the candidate rows carry Q7's full per-candidate transparency (every candidate, including `rejected_by_guardrail`, with heuristic attribution).

*Alternative named, not preferred:* one denormalised table (one row per candidate, cycle facts repeated per row). Set aside because it either duplicates cycle-level facts across up to seven rows (update-anomaly surface for the timeout/cost fields, which are only known at cycle end) or forces the cycle outcome to be derived at read time — both worse for an operational dashboard whose reader is a human.

**Proposed columns (build-time details flexible; the ruled fields are fixed):**

- `idea_loop_cycles`: `id` (uuid PK), `loop_id` (text, NOT NULL — the ruled required field), `cycle_number` (int), `gap_ref` (text — the settled `{sessionId}:{cycleNumber}:{currentCircle}->{targetCircle}` format; see §2.6 on composition), `cycle_outcome` (CHECK — §2.2's cycle vocabulary), `winner_candidate_id` (nullable FK), `friction_only_mode` (boolean — records the mode the cycle ran under; transparency only, never the counter itself, per §1 item 6), `cost_cents` (**integer** — the loop-billing integer-contract lesson; the runner aggregates from the guardrail calls' `X-Loop-Cost-Cents` headers + the winner consult's metering), `elapsed_ms` (int) and `maximum_duration_ms` (int — runner-declared; see §2.5's honesty note), `agent_id` (text), `owner_user_id` (uuid, FK → profiles ON DELETE CASCADE), `credential_ref` (text), `started_at`/`ended_at`, `created_at`, `retain_until` (see §2.7).
- `idea_loop_candidates`: `id` (uuid PK), `cycle_id` (FK → cycles ON DELETE CASCADE), `gap_ref`, `heuristic` (CHECK — the seven `GenerationHeuristic` values), `proposed_action` (text — full transparency per Q7 includes the refused proposals' text; this is the founder's operational dashboard, never served publicly), `classification_kind` (CHECK `virtue_domain | preferred_indifferent`) + `classified_domains` (text[]), `generation_confidence` (numeric), `guardrail_proximity` (text, nullable) + `guardrail_domains` (text[], nullable) — the ruled per-candidate guardrail result — plus `guardrail_session_id` (text, nullable; §2.5 traceability), `passed_novelty_check` (boolean, nullable), `novelty_confidence` (numeric, nullable), `novelty_basis` (text, nullable — carries `fresh`'s ruled `insufficient_history` basis when present), `cycle_outcome` (CHECK — §2.2's seven candidate values), `unavailable_dependency` (text, nullable).

House table discipline proposed as standard: RLS service-role-only; missing-table-benign reads; indexes on `(loop_id, cycle_number)` and `retain_until`; idempotent + reversible migration authored at build, founder-walked TEST → prod.

**One compatibility note, named not resolved:** the brief's §3 item 1 ruling requires the *generation-step scope document* to name how the runner handles a guardrail call that fails closed. The candidate row's guardrail fields are nullable and the outcome vocabulary is a CHECK, so the table can represent whatever that document rules (including, if ruled, a new token — a CHECK widening is the house-precedented additive path). ### 2.2 Outcome vocabularies — cycle level and candidate level

**PROPOSAL:** the **candidate-level** `cycle_outcome` CHECK carries the seven ruled values: `pending | rejected_by_guardrail | rejected_by_novelty | winner | null_cycle | dependency_unavailable | terminated_by_timeout` (the six committed values plus Q6's ruled seventh). The **cycle-level** `cycle_outcome` CHECK carries the four ruled outcomes, with the timeout token spelled **`terminated_by_timeout`** for uniformity with the candidate level: `winner | null_cycle | dependency_unavailable | terminated_by_timeout`. **[PR19, boundary F1 fold]** Q5's verbatim list spells the fourth outcome *"timeout"*; because this respelling rides a ruled value, it is raised explicitly as §3 **QW-C** rather than left as an unlabelled proposal.

The candidate-level `pending` value is legitimate in a **terminated** cycle's record only where Q6's ruling replaces it — *"leaving them 'pending' indefinitely is a false impression"* — so at build, a timeout cycle's unassessed candidates are written `terminated_by_timeout`, not `pending`. A `pending` row should only ever appear if the runner writes mid-cycle snapshots, which §2.3 does not propose (one write per completed cycle).

**Adjacent semantic surfaced for the mentor (part of §3 QW-A):** the corpus fixes when *candidate-level* `dependency_unavailable` occurs (a friction attempt finds the task list unreachable; the cycle continues on the other heuristics — brief Phase 1) but never states when the **cycle-level** outcome reads `dependency_unavailable`. The natural reading — proposed, not resolved: only when no active heuristic could produce an assessable pool at all, which concretely is the friction-only-mode case (friction is the sole active mechanism and its dependency is down). In normal mode a task-list outage is candidate-level only and the cycle's outcome comes from the other six heuristics. Since the table's CHECK enshrines the cycle-level vocabulary, this reading is put to the mentor rather than assumed (§3 QW-A(ii)).

### 2.5 Honesty posture — a runner-composed record, disclosed and traceable

## 3. Open questions for the mentor

*(Labels are `QW-*` — watching-prefixed — because the sibling `fresh` scope's own, already-ruled questions used `Q-A`/`Q-B` for different topics; the prefix prevents cross-document label collision in a sequence the mentor reads side by side.* **[PR19, boundary F2 fold]***)*

- **QW-A — the `dependency_unavailable` / fallback-counter distinction (the carried question, re-verified genuinely open).** Verified twice against the corpus (the predecessor session's close and again first-hand this session): the brief's §1.3 fallback rule counts *"three consecutive null cycles from heuristics 1–6"*; `dependency_unavailable` is stated only as *"honestly distinct from a null cycle"* (brief line 51); Q6 ruled only the seventh `cycleOutcome` value and never touched the counter. The pointer to "Q6's territory" resolves to nothing. So, per the ruling's own instruction, it is raised here rather than resolved by default. **(i) The counter question:** when a cycle's outcome is `dependency_unavailable`, does it (a) count toward the three, (b) reset the consecutive chain, or (c) pass transparently — the chain neither advances nor resets? *AI's analysis and recommendation: (c).* The counter's purpose is detecting novelty exhaustion of heuristics 1–6; a dependency outage carries no information about novelty. Option (a) has a perversity the mentor should see: candidate-level `dependency_unavailable` arises specifically from the shared task list being unreachable at a friction attempt (§1.4) — counting such cycles toward a trigger whose action is friction-detection-**only** mode would shift the loop toward the exact mechanism whose dependency failed. Option (b) would let an infrastructure outage silently erase evidence of genuine novelty exhaustion. **(ii) The cycle-level semantics (adjacent, surfaced in §2.2):** the corpus never states when the *cycle-level* outcome reads `dependency_unavailable`, given Phase 1 has the cycle continue on the other heuristics. Proposed reading, for ruling: only when no active heuristic could produce an assessable pool — concretely the friction-only-mode case; in normal mode the outage is candidate-level only. Under (c) + this reading, a friction-only-mode `dependency_unavailable` cycle also neither satisfies nor disturbs the fallback-exit condition (*"until a non-null cycle returns from an active mechanism"*) — it is not a non-null result from an active mechanism, and it is not a null cycle.
- **QW-B — the write path's capability class (§2.3):** `consult` reuse (the `fresh` capability ruling's reasoning), a dedicated `watching_write` capability added to the write-class set (the AI's recommendation — a durable-record write should carry write-class discipline; costs a founder-walked CHECK widening + the code constant + mint support), or another shape.
- **QW-C — the cycle-level timeout token's spelling (§2.2). [PR19, boundary F1 fold — raised here so it cannot be missed by a §3-oriented read.]** Q5's verbatim field list names the fourth outcome *"timeout"*; §2.2 proposes spelling the cycle-level CHECK token **`terminated_by_timeout`** for uniformity with Q6's ruled candidate-level seventh value. The semantic set is unchanged — this is a literal-token naming confirmation only. *AI recommends the uniform spelling.*

No other questions are open in this scope; everything else in §2 is a proposal for confirmation, and §1 is settled ground.
