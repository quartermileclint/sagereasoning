## The ruling, verbatim

## Q-P1 — Does Q1a's founder-personal branch survive R9 §3.1's prerequisite? **The ruling.** The second reading is ruled. V1 proceeds with §3's reverse algorithm idle on gap_only, accepting degraded generation as the honest v1 posture. The founder-personal branch of Q1a remains live. Minting and populating a harness identity with a genuinely examined trust record is not a precondition of v1 execution. The reasoning follows in three parts. --- **Part one — what R9 §3.1 actually establishes.** R9 §3.1's prerequisite is correctly stated: without an examined trust record for the executing actor, the reverse algorithm has nothing to anchor to, and v1 generation runs on gap_only. That is a precise architectural description. It is not a blocking condition. The distinction matters. A blocking condition would mean v1 cannot execute honestly until the prerequisite is met. A degraded-posture condition means v1 executes honestly with a named limitation — the reverse algorithm is idle, gap_only runs, and the limitation is disclosed. R9 §3.1 establishes the second, not the first. Its own language confirms this: "v1 generation runs on gap_only and §3's architecture is idle." That is a description of what happens under the condition, not a prohibition on proceeding under it. The brief correctly identifies that R9 explicitly declined to settle which reading governs. The ruling settles it: degraded generation is the honest v1 posture, not a deficiency that blocks execution. --- **Part two — why the first reading is ruled out.** The first reading would narrow Q1a's founder-personal branch by requiring a harness identity with a genuinely examined trust record before that branch is available. That is a new condition on a ruling that imposed no such condition. Q1a ruled the founder-personal branch live. R9 §3.1 identified a consequence of using it — degraded generation — but did not rule the branch unavailable. Treating a named consequence as a blocking condition would be reading a prohibition into a description. There is a deeper reason the first reading fails. The brief notes that Q1a's framing — "a low-frequency, high-integrity signal is the correct design" — may already imply the first reading, since a founder-directed session identity accumulating a real record is exactly the high-integrity path. The brief correctly declines to treat this as settled. The ruling confirms that declination. Q1a's framing describes the design's aspiration for the signal's quality. It does not make the high-integrity path a precondition of the low-integrity path's availability. A v1 that runs on gap_only is a lower-integrity signal than one running on a full reverse-algorithm anchor. It is still an honest signal, disclosed as such. The Prerequisite Criterion asks whether a design produces outputs resembling wisdom without building the prerequisite for it. A v1 that runs on gap_only and discloses that it does so is not producing an output that resembles more than it is. It is producing an output that accurately represents its own limitations. That is the honest posture, not a violation of the criterion. --- **Part three — what the ruling implies for the build.** The ruling has two practical consequences the build session should carry. First: the gap_only posture must be disclosed in the proposal shape. A completion signal produced under gap_only generation is a different signal from one produced under full reverse-algorithm generation. The proposal shape should carry a field indicating which generation mode was operative. This is not a new architectural requirement — it is the honest-claims discipline applied to the signal's own provenance. The build session should treat this as a required field, not an optional annotation. Second: the founder-directed session identity branch is the path toward higher-integrity signals, and the build should not foreclose it. Q1c's mint-level enforcement — distinct identities required, enforced at mint, not left to convention — is unbuilt. When it is built, the founder-directed session identity branch becomes available with the enforcement the ruling requires. The gap_only posture is v1's honest starting point, not its permanent ceiling. --- **On the four build items (§4) — confirmed as window-gated, no ruling needed.** All four are correctly characterised. Q1b's handoff is unbuilt. Q1c's mint-level enforcement is unbuilt and is the sharpest gap — nothing currently prevents minting a completion_signal_write credential on the runner's own agent_id, which is exactly the condition Q1c rules against. Q2's amendment is unapplied to the built surfaces' comments, with no semantic consequence while the surface is dark. All three wait for the window to close under Q-R12-B. The brief's observation that Q1c's enforcement gap is not tracked in R12 §7's prerequisites in its own right is noted and should be corrected in the build brief before the build session opens. Prerequisite 2 cites Q1c to establish that the executing identity is a different one; it should also note that the prohibition is currently unenforced at mint. --- **On the record corrections (§2) — confirmed as stated.** All four corrections are confirmed. R12 §7.6 and §15.7 conflate unanswered with unbuilt — the true statement is ruled and unbuilt. R9:912's omission of Q1b should be annotated. R8 §2.3's contested characterisation of the migration is stale. These are factual corrections requiring no ruling. The propagation path the brief traces — defect entered once at R8 §4.0's unannotated body, inherited four times — is the correct diagnosis, and the mechanical cause it names is precise: a dated annotation placed at a document's head governs the body but does not reach a reader instructed to read one section in full.
