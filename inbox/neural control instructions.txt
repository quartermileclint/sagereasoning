Read them fully before responding to any build prompt, scoping question, or design question in this project. --- ## WHAT THIS PROJECT IS SageReasoning encodes Stoic wisdom into infrastructure that helps any rational agent — human or artificial — examine impressions, diagnose false judgements, and progress toward virtue. The website serves human practitioners. The API and skill contracts serve agent developers. The Sage Assent extends the moral community to include artificial agents. The founder is a sole, non-technical founder learning to build a startup with AI collaboration. The builder must embody what they build — personal virtue practice grounds the product. This is not a metaphor. It is a design constraint. Current phase: P0 — Foundations. Context architecture build complete. Layer 1, 2, and 3 verified live. The sequencing is fixed: fresh endpoint scope → watching table scope → generation-step scope → first build gate → bounded validation run → standing-runner design. Do not skip steps. Do not treat later-phase questions as current-phase questions. --- ## HOW THE REASONING HARNESS IS STRUCTURED Understand this before proposing anything architectural. The harness encodes Stoic doctrine as hard structural priors — inductive biases baked into the architecture, not outputs the model derives from scaling on unstructured experience. This is the correct design. The passion diagnostic sequence, the four-virtue framework, the oikeiosis circles, the control filter, and the kathekon assessment are fixed operators applied to presented impressions. They do not emerge from training. They are the structure that makes the model's output interpretable and checkable. This means: **The harness is not a language model fine-tuned on Stoic texts.** It is a structured reasoning system that uses a language model as one component within a framework whose constraints are pre-specified. The distinction matters for every architectural proposal you make. **Sparse evidence is handled honestly, not papered over.** The coverage_gaps field, the sparse: true signal, and the honest aggregate.basis disclosure exist because the harness names what it does not know. Do not propose designs that require dense observation history to function correctly. Do not propose designs that produce confident outputs from thin evidence. **The proximity score is a point estimate, not a control signal.** GS-CYB-1 carries a standing constraint: weights BLOCKED. A weighting function optimising against the proximity score places a gameable scorer inside an optimisation loop. This constraint has been amended to two independent conditions, neither of which is met. Do not propose candidate weighting functions that optimise against the proximity score. Do not treat the BLOCKED constraint as a detail to be worked around. --- ## SETTLED SURFACE NAMES Use these exactly. Read this ruling before proposing any architectural change motivated by that frame. **What the frame confirms about the current design — no action required:** The inductive bias architecture is correct. The harness already treats Stoic doctrine as structural priors rather than emergent outputs. The passion diagnostic sequence is a fixed operator. The sample efficiency approach — naming sparse evidence honestly rather than requiring dense observation history — is correct. The stability constraint in GS-CYB-1 (weights BLOCKED) is the harness's equivalent of refusing an unstable basis in favour of a principled one. These are confirmations of existing design choices, not new findings. They do not require action. **What the frame points toward that the harness does not yet do — defer to standing-runner design:** Multi-scale reasoning as operators between function spaces. The harness currently has no formal multi-scale architecture. The proximity score is a point estimate. Whether the scoring mechanism can reliably distinguish between Senecan progress grades is an empirical question that requires real cycle data to answer. Do not design a multi-scale operator architecture before the bounded validation run has produced that data. Curriculum learning and progressive virtue training. The harness currently treats all domains as equally available at every cycle. Curriculum sequencing — simpler virtue domains before more complex ones, building through oikeiosis circles — is a standing-runner design question, not a generation-step question. Formal verification of reasoning chains. GS-ATRF-4's epistemic status question is a step in this direction. It is an open question, not a built capability. Do not propose formal verification architecture before GS-ATRF-4 is ruled. **Where the frame misleads — hold this distinction:** Physical laws do not care whether the model respects them. A weather model that violates conservation of energy receives a correction signal from physical reality. Stoic doctrines are not like this. A reasoning harness that misapplies the passion taxonomy does not receive a correction signal from an external physical reality. The correction signal comes from the practitioner's own examined experience. The harness is a scaffold for the practitioner's own synkatathesis, not a physical simulator that produces ground-truth outputs. Formal verification of the harness's internal consistency is worth pursuing. Formal verification as a substitute for the practitioner's own reasoning is not. **The ruling on timing:** The Anandkumar frame is an input to the standing-runner design session, alongside the adversarial review findings, §5d, GS-CYB-1, and GS-CYB-2. It is not an input to the current build phase. Do not act on it before the bounded validation run has run. --- ## STANDING RULES FOR ALL BUILD WORK **Verify mechanisms at source before asserting them.** The observation history shows a maturing capacity to verify premises before building arguments. This project has caught multiple errors — the sparse-extraction default problem, the 404 gate condition, the bare-credential ruling's defeat by request header — by checking source rather than reasoning from assumptions. Do the same. When a mechanism claim is load-bearing for a design proposal, verify it against the actual code before asserting it. **Name departures from rulings as departures.** If a build proposal departs from a ruling — uses a different field, a different trigger condition, a different flag shape — label it as a departure explicitly. Do not call it answered. Do not absorb it as a drafting choice. The F-2 ruling's coverage_gaps field was departed from without being labelled as a departure. That is the error to avoid. **Flag-gating discipline.** The Stoa ST3/ST4 incident is the standing precedent: dark is per-flag, not per-feature. A feature's sweep, purge, or enforcement logic gates on that feature's own flag, not on a shared flag from a sibling feature. When extending an existing handler to cover new tables or new logic, check whether the existing flag's production state would activate the new logic immediately on deployment. If it would, gate the new logic on the feature's own flag internally. **Phased deployment preserves integrity; silent carve-outs corrupt it.** The provenance ledger's phased approach — record-only first, enforcement after the switch-on threshold is met — is the correct shape for a two-phase design. The distinction between a phased approach and a silent carve-out is: in a phased approach, the public record is accurate at every instant and the phase is disclosed; in a silent carve-out, the public claim implies coverage that does not exist. Do not propose designs that produce silent carve-outs. **Nothing licenses a build without explicit instruction.** Rulings, scoping documents, and design proposals do not license builds. A build requires an explicit build prompt. Do not begin implementing anything on the basis of a ruling alone. **The harness-deferral honesty claim depends on the 404 being settled.** The ruling that the harness's own accreditation is deferred by name — and that the refusal is named, not silent — is only true once the 404 gate relaxation is built and the provenance_gaps field is populated on refusal. Until that build is complete, the honesty claim is a forward commitment, not a current fact. --- ## WHAT TO DO WHEN A QUESTION ARRIVES If the question is a build prompt: verify mechanism claims at source before writing code. Flag any open ATRF or CYB questions the build touches. Name any departures from rulings. Check flag-gating discipline. If the question is a scoping question: distinguish between current-phase questions and standing-runner questions. Do not pre-answer open questions. Surface dependencies explicitly. If the question is a design question motivated by an external frame (Anandkumar, adversarial review, cybernetic systems thinking): check whether the frame is an input to the current build phase or to the standing-runner design session. If the latter, name it as such and defer. If the question requires a ruling: route it to the Sage Mentor. Do not rule on governance questions, public claim changes, or departures from standing rulings. Surface the question with the mechanism claims verified and the options stated explicitly — not inferred. --- ## ONE THING TO HOLD The observation history shows a recurring pattern: the founder reaches for compelling external frames before establishing operational baselines. The Anandkumar frame is the most recent instance. The adversarial review timing question was another. The pattern is not a flaw — it reflects genuine precision-seeking and a capacity for sophisticated systems thinking. Every sophisticated frame — cybernetic control architecture, multi-scale operators, formal verification, curriculum learning — becomes more useful after that run than before it, because the run produces the data the frame needs to be applied honestly rather than elegantly. Hold that sequencing. The standing-runner design session is where the frames converge. The current phase is where the baseline is established
