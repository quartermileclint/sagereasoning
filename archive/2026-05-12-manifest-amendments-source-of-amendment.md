## R17 — Intimate Data Protection (EXPANDED)

Current R17 covers R17a-f. Expansion per ST2 Phase 3 Step 8 Domain 4 P2 (REVISE — phased):

### R17g — Subject Access Request handling (NEW; Critical surface)

**Rule:** When a user requests access to their data (GDPR Article 15), the substrate produces a structured export within 30 days containing all stored data attributable to that user, including: mentor profile fields, journal ingestion content, decision-log mentions, audit trail entries, and any third-party data the substrate has retained.

**Implementation surface:** `/api/user/access` endpoint (NEW). Authenticated; rate-limited; logs every request in operations decision log.

**Sequencing:** Lands after A15a (R17c genuine deletion endpoint). Phase 4 sub-stage A15b.

### R17h — Rectification handling (NEW; Critical surface)

**Rule:** When a user requests rectification of inaccurate data (GDPR Article 16), the substrate updates the named fields within 30 days. Rectification is logged with before/after values in an immutable audit row.

**Implementation surface:** `/api/user/rectify` endpoint (NEW). Same governance as R17g.

**Sequencing:** Phase 4 sub-stage A15c.

### R17i — Portability handling (NEW; Critical surface)

**Rule:** When a user requests data portability (GDPR Article 20), the substrate produces a machine-readable structured export of all user-supplied data (not derived data) within 30 days, in a commonly-used format (JSON; CSV for tabular structures).

**Implementation surface:** `/api/user/export` endpoint (NEW). Same governance as R17g.

**Sequencing:** Phase 4 sub-stage A15d (most complex; export-format ADR may precede implementation).

## AC additions — Architectural Constraints

### AC9 — Layer2Decision four-outcome envelope (NEW)

**Source:** ST2 Phase 3 Step 2 Amendment 2A (REVISE).

**Constraint:** Layer 2 outputs include a top-level `decision` field with values from `{ALLOW, BLOCK, REVISE, ESCALATE}`. The decision is derived from existing mechanism outputs (allowance flags + value-assessment scores) via a deterministic rule set documented in `/website/src/lib/layer2-decision-mapping.ts`. The categorical decision is exposed alongside the existing Layer2Assessment fields (mechanism outputs); both are available to consumers.

**Rationale:** Aligns Layer 2 outputs with the OpenBrain Judge Extender contract vocabulary; gives downstream consumers a clean routing field; preserves existing mechanism outputs for fine-grained consumers.

### AC10 — Provenance + use-policy tags (NEW)

**Source:** ST2 Phase 3 Step 2 Amendment 2B (REVISE — Layer2 first).

**Constraint:** Every Layer 2 assessment output carries:
- `provenance`: one of `{observed, inferred, user_confirmed, generated}` per OpenBrain Judge Extender contract
- `use_policies`: array of `{advisory, binding_within_session, binding_cross_session, requires_founder_approval}`

The decision-log adopts these tags as a separate amendment (Phase 4-2 work) once the Layer 2 output discipline proves the pattern.

### AC11 — OpenTelemetry GenAI semantic conventions (NEW)

**Source:** ST2 Phase 3 Step 8 Domain 5 O1 (ALLOW).

**Constraint:** All substrate operations are instrumented per OpenTelemetry GenAI semantic conventions. Auto-instrumentation for Anthropic SDK; trace propagation across Layer 1 → Layer 2 → Layer 3 → Supabase write; correlation IDs preserved across the plugin → substrate boundary.

**Cross-references:** Enables AC10 call-grain provenance logging; AC1 cost telemetry (R5); per-identity behavioural baselines (S1 / A10).

### AC12 — Sub-agent verification (NEW)

**Source:** ST2 Phase 3 Step 5 Candidate 2 (ALLOW Sub-Agents).

**Constraint:** Critical-tier verification steps (per AC4 invocation testing) MAY be performed by a verifier sub-agent that independently runs the production scenarios and reports. The sub-agent's report is appended to the decision-log entry as a verification artefact.

**Rationale:** Replaces the Jest configuration debt (F-series stewardship); closes the "agent self-reports verification" gap (Theme G hallucinated audit trails per inbox synthesis).

### AC13 — Outcomes-grader option (NEW)

**Source:** ST2 Phase 3 Step 5 Candidate 6 (ALLOW with pre-condition).

**Constraint:** PR1 single-endpoint-proof verification MAY use Anthropic Outcomes (rubric + separate-grader pattern) as an additional verification layer. Adoption is cost-aware: when Outcomes evaluation cost per session is < R5 cost-as-health-metric session-budget, use it; otherwise rely on standard verification.

**Pre-condition:** Outcomes pricing confirmed against R5 thresholds before first use.
